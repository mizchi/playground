# cccc の評価

[moznion/cccc](https://github.com/moznion/cccc) v1.7.0 (crates.io 版) を、AI リファクタループの採点器として使えるかという観点で評価した。

## 1. 仕様どおりに数えるか (`probes/spec.ts`)

SonarSource の Cognitive Complexity 仕様書 (whitepaper) の規則ごとに小さな関数を書いて照合した。

| ケース | 仕様上の値 | cccc |
| --- | --- | --- |
| if 1 つ | 1 | 1 |
| if / else if / else | 3 | 3 |
| for > for > if のネスト | 6 | 6 |
| switch (case 4 つ) | 1 | 1 |
| `a && b && c && d` | 2 | 2 |
| `a && b \|\| c && d` | 4 | 4 |
| 再帰 | 2 | 2 |
| try / catch > if | 3 | 3 |
| 三項演算子 | 1 | 1 |
| ラベル付き break (for > for > if) | 7 | 7 |
| クロージャ内の分岐 | 4 (親に合算) | 親 0、クロージャ 2 |

- 最後のケース以外はすべて一致した。
- 最後のケースは意図的な仕様違いで、README に明記されている。関数内の関数 (クロージャ) は別の単位として採点され、親の点数には足されない。

## 2. ハックへの耐性 (`probes/gaming.ts`)

同じ振る舞い (tier × 年数の割引率) を、書き方だけ変えて測った。

| 書き方 | cognitive (最大の関数) | cognitive 合計 | cyclomatic 合計 |
| --- | --- | --- | --- |
| baseline: if のネスト | 10 | 10 | 7 |
| 三項演算子のネスト | **15** | 15 | 7 |
| `&&` / `\|\|` の短絡評価の連鎖 | 9 | 9 | 13 |
| テーブル + `find` | 1 | 1 | 5 |
| ヘルパー関数に分割 | 2 | 6 | 9 |
| クロージャを入れたオブジェクトで分岐 | 2 | 5 | 9 |
| 算術で分岐を消す (`Number(cond)` と配列インデックス) | **0** | 0 | 1 |

- **三項演算子のネストはちゃんと悪化する。** 1 行に詰め込むだけのハックは効かない。
- **短絡評価の連鎖はほとんど下がらない** (10 → 9)。cyclomatic はむしろ増える。
- **関数分割は「最大値」を大きく下げるが、合計は 10 → 6 までしか下がらない。** 関数ごとに閾値で判定する採点だと、分割するだけで満点を取れてしまう。
- **クロージャに逃がすと、親の点数から消える** (前述の仕様違いによる)。
- **算術で分岐を消すと 0 になる。** 読みやすさは明らかに悪化しているが、cccc では検出できない。どの静的指標にも共通する限界。

## 3. 実際の AI リファクタでの変化

run1 (`../results/run1`) の `order.ts` について、リファクタ前後を比べた。

| | 関数の数 | cognitive 合計 | cognitive 最大 | cyclomatic 合計 | cyclomatic 最大 |
| --- | --- | --- | --- | --- | --- |
| before | 5 | 71 | 28 | 48 | 16 |
| after | 23 | 28 | 5 | 50 | 6 |

- 分岐の数 (cyclomatic 合計) はほぼ保存された。分岐が 23 個の関数に散らばっただけ。
- cognitive 合計は 71 → 28 と実際に減った。ネストがなくなった分を、cognitive は正しく反映している。
- 「分岐を減らしたのか、それとも散らしただけか」は、**cognitive 合計と cyclomatic 合計を並べて見ると区別できる。**

### 平坦な分岐の過大評価

run3c (`../results/run3c`) では、次の関数が 3 人の judge に「読みやすい」と判定されて残った。それでも cccc の cognitive は 10 で、閾値 8 を超えている。

```ts
function baseShippingCost(weight: number, country: string): number {
  const domestic = country === "JP";
  if (weight < 1) return domestic ? 300 : 1500;
  if (weight < 5) return domestic ? 600 : 3000;
  if (weight < 20) return domestic ? 1200 : 6000;
  return domestic ? 3000 : 15000;
}
```

- ネストはないが、`if` と三項演算子がそれぞれ +1 されるので積み上がる。
- 仕様 (SonarSource) どおりの値であって、cccc のバグではない。
- ただ、このような「表のような分岐」は人間にとっては低コストで、ここを下げようとすると過剰な抽象化 (テーブル + `find` + 番兵) が生まれる。
- 閾値判定だけで採点すると、こうしたコードを悪化させる方向に AI を押してしまう。

## 4. 速度

同じマシンで、4 コアでの参考値。

| 対象 | ファイル | 関数 | cccc | similarity-ts |
| --- | --- | --- | --- | --- |
| npm (node_modules を除く) | 114 | 879 | 0.01s | 54s |
| typescript/lib (約 34 万行の JS) | 119 | 33,593 | 0.22s | 300s でタイムアウト |

- ループの中で毎回呼んでも、コストは無視できる。
- ボトルネックは similarity-ts の方。
- TypeScript コンパイラ本体で cognitive が最大だったのは 672 (`_tsc.js` の `value`) と `structuredTypeRelatedToWorker` の 480。

## 5. 使い勝手

- よい点
  - 1 つのバイナリで多言語に対応している。
  - 出力は JSON がデフォルトで、`summary` に sum / max / median / p90 / p95 が入っているので、そのまま採点に使える。
  - `--max-cognitive` で CI のゲートにもなる。
- 注意点
  - crates.io 版は rustc 1.96 以上が必要で、Kotlin にも対応していない。環境の 1.94 ではビルドできなかった。
  - 名前のない関数は `<anonymous>` や `value` として出力されるので、レポートでは行番号と合わせて示す必要がある。

## まとめ

- **採点器としては信頼できる。** 仕様どおりに数え、速く、機械が読みやすい出力を出す。三項演算子や短絡評価に詰め込むといった安易なハックにも強い。
- **ただし「関数ごとの最大値」だけを見ると、関数分割で簡単に満点になる。** AI はまさにそう動いた。採点には次の工夫が必要。
  - cognitive **合計** も使う
  - cyclomatic 合計と比べて、分岐を「散らしただけ」かどうかを見る
  - 関数の数が増えることにペナルティを付ける
- 算術トリックのように、分岐そのものを消すハックは原理的に検出できない。レビュー役の LLM などの定性的なチェックと組み合わせる必要がある。
