**VERDICT: better**

**Why:** Most extractions are genuine deduplication, not cosmetic splitting. The rate tables (`MEMBER_RATES`/`GOLD_RATES`, `SHIPPING_RATES_JP`/`_OTHER`) turn three duplicated if/else-if ladders into data + one lookup function — that's a real maintainability win (adding a tier or country tier now means editing a table, not copy-pasting branches). `round2`/`subtotalOf` eliminate three copies of `Math.round(x*100)/100` and two copies of the subtotal loop. The validation split (`validateUser`/`validateItem`/`validateItems`/`validateCoupon` composed via spread in `validateOrder`) reads cleanly and removes the nested-else-inside-else structure from the original. Behavior is preserved (`item.price<0` → else-if `qty<=0` → else-if furniture check still short-circuits the same way).

**Things that smell like metric-chasing rather than real clarity gains:**

1. **`itemWeight`/`totalWeight` split** — `itemWeight` is used exactly once (inside `totalWeight`'s reduce). There's no reuse to justify pulling it out; it just turns one small loop into two functions, likely to shave cyclomatic complexity/line count off `calculateShipping`. Inlining it back would be no less readable.
2. **`discount = calculateMemberDiscount(...) + calculateGoldDiscount(...)`** in `calculateTotal` — this is a behavior-preserving but *less explicit* rewrite of the original `if (member) ... else if (gold) ...`. It only works because `tierDiscount` silently returns 0 for a non-matching tier — an invariant a reader has to reconstruct rather than see stated. If a future tier is ever allowed to combine with another (or if `tierDiscount`'s zero-return contract is ever violated), this silently double-applies discounts. The original if/else made "at most one tier discount" visually obvious; the new code makes it an implicit assumption. This is the one place I'd push back on in review — not dangerous today, but a small maintainability regression dressed up as a simplification.
3. Minor: `tierDiscount(user, subtotal, tier, rates)` passes `tier` in just to re-compare it against `user.tier` inside the function — a bit of indirection for what's still effectively "is this the right tier," though it is reused twice so it's defensible.

None of this rises to obvious gaming (e.g., splitting a 2-line function into two 1-line functions purely to inflate function count, or renaming without restructuring), but #1 and #2 are the kind of change that improves a complexity/duplication *score* slightly more than it improves actual comprehension.
