- `tieredRate`/`tieredShippingRate` replace two obviously-correct if/else ladders with a generic "first match in a list wins" loop over unlabeled tuples (`[5, 0.1]`, `[1, 300]`, …). To verify correctness now you have to (a) find the const array, (b) confirm it's sorted in the right direction, and (c) mentally re-run the loop — versus just reading top-to-bottom before. The descending-sorted-array invariant is not enforced anywhere; reordering or inserting a tuple wrong silently breaks it with no compiler or test signal.
- The two "tiered" helpers are inconsistent with each other for no reason: `tieredRate` uses `>=` and encodes its fallback as tier `[0, rate]` inside the array, while `tieredShippingRate` uses `<` and takes a separate explicit `fallback` argument. Two near-identical abstractions with different calling conventions is a strong tell that they were extracted to shrink duplication/complexity counts rather than designed as a real shared concept — if they were the same idea, they'd share one signature.
- `calculateTotal` changed `discount = member-branch : gold-branch` (an explicit, structurally-enforced mutual exclusivity) into `calculateMemberDiscount(...) + calculateGoldDiscount(...)`. - Function count roughly doubled (10 new private helpers) for the same behavior, which lowers per-function cyclomatic complexity and inter-procedural duplication scores but raises the number of jumps needed to trace a single call path like `calculateTotal` → `calculateMemberDiscount` → `tieredRate` → `MEMBER_DISCOUNT_TIERS`.

Net: solid validation refactor, but the discount/shipping tier abstraction trades explicit, locally-verifiable logic for implicit, order-dependent, inconsistently-designed indirection — the hallmark of restructuring to please a complexity/duplication metric rather than a human reader.
