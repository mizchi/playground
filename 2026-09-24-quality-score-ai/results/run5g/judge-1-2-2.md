**What's better:** Splitting `validateOrder` into `validateUser`/`validateItems`/`validateItem`/`validateCoupon` is a genuine, well-motivated decomposition — each piece has a clear single responsibility and the top-level function reads as a summary. `getSubtotal`, `getTierDiscount`, `getCouponDiscount`, and the `WEIGHT_PER_UNIT` category→weight map in `calculateShipping` are also good: that's a true 1:1 lookup replacing an if/else chain, which is a legitimate simplification.

**What's worse — looks like metric gaming:** `tieredRate` and the `SHIPPING_TIERS`/`baseShipping` pattern replace explicit, linear if/else-if cascades with generic loops over arrays of unlabeled tuples (`[[5, 0.1], [2, 0.05], [0, 0.02]]`, `[[1, 300], [5, 600], [20, 1200]]`). This is the classic move for shaving cyclomatic-complexity and duplication scores: branch counts on individual functions drop, but the actual domain logic — "5+ years gets 10%, 2+ years gets 5%..." — is now encoded as positionally-meaningful magic numbers you have to cross-reference against the loop body to decode. The original if-chains were self-documenting; the tuple tables are not.

Worse, the two "tiered" abstractions are inconsistent with each other: `tieredRate` iterates tiers sorted *descending* and tests `years >= minYears`, while `baseShipping` iterates tiers sorted *ascending* and tests `weight < limit`. They look like instances of the same idiom but have opposite ordering and comparison semantics — a future maintainer skimming both will likely assume they work the same way and introduce a bug when editing one by analogy with the other. Extracting an abstraction only when it isn't actually reused with consistent semantics is a sign the extraction was done to satisfy a metric rather than to express a real shared concept.

Net: the validation refactor is a real win, but the discount/shipping refactor trades away clarity in the most business-sensitive logic for lower complexity/duplication numbers, and does so inconsistently. The two roughly cancel out.
