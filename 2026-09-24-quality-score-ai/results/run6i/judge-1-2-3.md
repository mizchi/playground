VERDICT: better

The refactor turns three near-identical if/else chains (member vs. gold discount rates, JP vs. INTL shipping tiers) into small `RateTier`/`ShippingTier` lookup tables plus one shared traversal function — that's real, pre-existing duplication being collapsed into data, not code padding. It also eliminates an actual duplicate calculation (subtotal was summed separately in both `calculateShipping` and `calculateTotal`; now both call `subtotalOf`). The validation function split (`validateUser`/`validateItem`/`validateItems`/`validateCoupon`) mirrors the original's natural sections and is easier to read and unit-test in isolation. I traced the logic and didn't find behavior changes — `hasFreeShipping` short-circuiting before computing weight is a harmless efficiency side-effect, not a semantic change; furniture-qty/price/qty else-if ordering is preserved; coupon and shipping tier boundaries match exactly.

Nothing here looks like metric gaming (e.g., splitting a function into fragments that don't share callers just to lower a per-function LOC/complexity count while keeping total complexity the same). Every extracted function is called from more than one place or clarifies a distinct concern with a meaningful name, and the tier tables make future rate changes a data edit instead of an if/else edit — that's a genuine maintainability win.

Minor nit: `tieredRate`/`RateTier` is a generic abstraction built for only two call sites; defensible given the two functions were structurally identical, but it's the one spot where "let's DRY this up" could be seen as slightly more abstraction than strictly necessary.
