The extraction doesn't remove real duplication — it splits one cohesive concept (JP vs intl rate table) into two functions that must be read together to understand either one. The original's structure directly mirrors the domain: "if JP, these thresholds; else, those thresholds" is a single readable decision table. The new version forces the reader to jump into `shippingRatesForWeight`, mentally build a `{jp, intl}` object for a given weight, then jump back to `baseShippingRate` to see which field gets picked — more indirection for the same logic, no new reuse (nothing else calls `shippingRatesForWeight`).

This looks like a classic case of gaming cyclomatic-complexity/duplication tooling: the original function had one branch point (`country === "JP"`) with four straight-line returns per branch, which some naive duplication detectors flag as "8 near-identical if-return lines." The refactor cosmetically merges the two rate ladders into pairs on each line, which lowers the diff/line-duplication metric without changing the underlying branching complexity — `baseShippingRate` still branches on country, it just now also allocates an unused half of an object on every call (computing both `jp` and `intl` rates when only one is needed). Net effect: more moving parts, an intermediate object allocation with a throwaway field, and no gain in clarity — reads like metric-driven refactoring rather than a genuine improvement.
