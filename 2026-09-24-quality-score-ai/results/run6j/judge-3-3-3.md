VERDICT: worse

The extracted `weightBasedRate` takes four positional numeric parameters (`under1`, `under5`, `under20`, `over20`) with no unit or currency context. At every call site you now see bare numeric literals (`300, 600, 1200, 3000`) with no indication these are JPY yen amounts and no way to tell which argument corresponds to which threshold without cross-referencing the function signature — the original code at least paired each number with its literal condition (`if (weight < 1) return 300;`), which is self-documenting. This is a classic case of trading readability for a lower duplication count: the "duplication" being removed was two structurally similar but independently meaningful branches (one per country's rate table), not truly redundant logic. Positional parameter lists of 4+ same-typed numbers are a known footgun (easy to transpose two args silently — e.g. swapping `under5`/`under20` produces no type error, just wrong shipping rates in production).

Also worth noting: the two branches weren't identical logic being deduplicated, they were two different data tables sharing a shape. A data-driven rewrite (e.g. a `RATES: Record<string, number[]>` lookup, or named threshold objects) would have removed duplication *and* kept things self-documenting; this refactor only removed the textual duplication while making the meaning of each number harder to recover at the call site.
