# 人間の確認が必要なもの

自動テストでは確かめられないもの、人の判断や mac の環境が要るものをまとめる。自動で確かめたことは [VALIDATION.md](./VALIDATION.md) にある。

## 準備

```sh
cd 2026-11-21-ai-native-desktop/proto-canvas
pnpm install
pnpm dev          # http://127.0.0.1:8123 をブラウザで開く
```

- Node 24 以上が必要
- 件数や窓の数を増やすときは、URL に `?todos=1000&extra=7` を付ける

各項目は、次の形で書いている。

- **何を**: 確かめること
- **手順**: やること
- **見るところ**: 判断の材料
- **記録**: 結果を書く場所。この文書の各項目の「結果」欄に、日付と一言を書けばよい

## H1. 承認の UX (承認疲れ・プレビューの伝わり方)

**何を**: AI の提案を人が無理なく承認できるか。プレビューを見て、実行後の結果を正しく予想できるか。

**手順**

1. パネルの「例: 操作」「例: レイアウト」で提案を出し、承認する前に「実行後どうなるか」を口に出して言う。そのあと承認し、予想と合っていたかを見る
2. 自分で手順を書き換えた提案を 10 個ほど出す
   - 操作とレイアウトを混ぜる
   - sensitive な操作 (利用状況の送信、全データを削除) を混ぜる
3. 「sensitive でない提案は自動承認」をオン / オフにして、承認を求められる回数を比べる
4. 提案を出したあと、承認する前に同じスイッチを自分で操作し、承認する。「古い提案 (stale)」になって実行されないことを見る

**見るところ**

- 破線の枠と番号 (操作)、破線と「→ ここ」のラベル (レイアウト) で、結果を予想できたか
- 承認を求められる回数が、煩わしくない程度か。どの粒度のポリシーなら許せるか
  - 例: アプリ単位、action 単位、10 分間など期限付き
- stale になったとき、理由が分かるか (監査ログの表示で足りるか)

**記録**: 予想が外れた提案と、その理由。欲しいポリシーの粒度。

## H2. ドラッグ&ドロップとアニメーションの操作感

**何を**: 窓の配置換えが「気持ちよく」感じられるか。

**手順**

1. タイトルバーを掴んで、次の場所へ運ぶ
   - ペーンの端・中央・タイトルバー
   - 境界
   - 外周
   - 下に現れる「最小化」の受け口
2. パネルの「ライブプレビュー」をオンにして、同じことをする
3. 境界のダブルクリック、タイトルバーのダブルクリック、Alt+方向キー / Alt+Enter / Alt+M / Alt+E を試す
4. 1000 件の Todo (`?todos=1000`) で、ホイールでのスクロールと、Tab で一番下まで移動したときの動きを見る

**見るところ**

- 落とす先の判定の帯の幅が、狙いどおりに感じられるか
  - ペーンの端 28%、外周 28px、境界 12px (`src/tiling.ts` の `PANE_ZONE` / `ROOT_BAND` / `INSERT_BAND`)
- ばねの硬さと弾み (`src/anim.ts` の `TILE_SPRING` / `PREVIEW_SPRING`)
- overlay とライブプレビューのどちらが分かりやすいか
- 赤いプレビュー (最小幅を下回る) の理由が読めるか

**記録**: 変えたい定数と値。どちらのプレビューを既定にするか。

## H3. 実際の日本語 IME (mac)

**何を**: OS の IME を、Canvas の上で違和感なく使えるか。自動テストでは CDP で composition を擬似的に起こしただけ。

**手順**

1. mac の Chrome / Safari / Firefox で開く
2. Todo の「新しいタスク」に、日本語入力で「たまごをかう」と打ち、変換して確定する
3. 変換中に Esc、Backspace、文節の移動を試す
4. 確定後に Backspace で 1 文字ずつ消す

**見るところ**

- 変換候補のウィンドウが、キャレットの近くに出るか
- 変換中の文字 (下線付き) が、入力欄の中に正しく描かれるか
- 確定した文字だけが値になるか (パネルの意味ツリーで確かめる)
- Safari と Firefox で挙動が違わないか (EditContext を使っていないので、隠し textarea の挙動に依存する)

**記録**: ブラウザごとの不具合。

**結果**: (未記入)

**何を**: 意味ツリーから作る ARIA のミラー DOM を、実際のスクリーンリーダーで読み上げ・操作できるか。

**手順**

1. mac で VoiceOver をオンにして (Cmd+F5)、ページを開く

3. VO+Space でチェックボックスを切り替え、ボタンを押す
4. ローター (VO+U) で見出しやフォーム部品の一覧が出るか

**見るところ**: 読み上げの順、役割と名前、状態 (チェック済みなど)、操作が Canvas の表示に反映されるか

**記録**: 読み上げが不自然な箇所。

## H5. Odin backend (済)

Odin のビルドの許可を得て、wasm 版の backend をブラウザで確かめた (VALIDATION.md の 4a)。mac の単体アプリ (SDL3 の窓) での確認は、まだしていない。

- 手元で試すとき: `/home/user/tools/odin` にビルドした Odin があれば、次を実行する

  ```sh
  PATH=/home/user/tools/odin:$PATH pnpm build:odin && pnpm fonts && pnpm build
  ```

  そのうえで `?backend=odin&font=fonts/ipaexg.ttf` を付けて開く

**結果**: 2026-11-22 許可を得てビルドし、E2E がすべて通った。

## H10. 実際の AI クライアントから MCP でつなぐ

**何を**: Claude Code などの MCP クライアントから、AI が `get_tree` で状態を読み、`propose` で提案し、人が画面で承認する流れが、実際に使えるか。通しの動きは自動テストで確かめた (VALIDATION.md の 7)。ここで見るのは、AI がツリーを正しく読めるかと、提案の文の分かりやすさ。

**手順**

1. `pnpm dev` を動かし、ブラウザで `http://127.0.0.1:8123/?mcp=ws://127.0.0.1:8130` を開く
2. MCP クライアントに、`node mcp/server.ts` (作業ディレクトリは `proto-canvas`) を stdio のサーバとして登録する
3. 「牛乳を完了にして」「Settings を最小化して、残りを均等にして」のように頼み、画面に出た提案を承認する / 却下する

**見るところ**

- AI が目的のノードを正しく選べるか
- 提案の intent が、人の判断に足りるか
- 拒否や stale の理由を、AI が読んで直せるか

**記録**: AI が迷った操作。

**結果**: (未記入。API の費用がかかる)
