# メモ：小さい ML をシステムの判断に入れる（2026-11-23〜24）

この実験でやったことと、分かったことのまとめ。詳細は各ファイルにある。

| 知りたいこと | 場所 |
|---|---|
| いつ使うか、何を使うか、各手段の評価 | `GUIDE.md` |
| 計測の生データと再現手順 | `bench/README.md`、`bench/onnx/README.md`、`templates/RESULT.md` |
| すぐ使える雛形（TS・Rust・Python・Julia） | `templates/README.md` |
| 図つきの解説（`mizchi/explainer` スキル、検証済み） | `explainer/README.md` |

数字はすべて 4 コアの Linux での 1 回ずつの計測で、データは合成。キャッシュ容量は 0.5%。
OHR はリクエスト数で数えたヒット率（応答の速さに効く）、BHR はバイト数で数えたヒット率（裏側への転送量に効く）。

## 結論

1. **製品の中の同期の判断には、自前の小さいモデル（LR・MLP、重み数百個）が一番合う。** 1 行の推論は Rust 105〜185ns、TS 427ns。ONNX ランタイム（4.6〜12µs）・WebNN（35〜50µs）・Python（2.9〜90µs）は 1 回の呼び出しの手間が大きい。学習はどの言語でも 1 秒かからず、重みを共通の JSON にすれば 4 言語のどれで学習しても TS・Rust にそのまま読み込める（予測の差 2.4e-7 以下）。
2. **ML を入れる前に、単純なルールと定番のキャッシュと比べる。** OHR では `moka`（ML なし）の約 36% が、ML の admission（23〜27%）を大きく上回った。ML の admission が勝ったのは BHR（17.5%）だけ。
3. **最も効いたのは、微分可能プログラミングでヒット率そのものを最適化すること。** 代わりのラベルではなく「容量の制約の下でのヒット」を損失に書いて TTL を学習すると、OHR 40.0%。OHR と BHR を混ぜた目的（α=0.4）に頻度の門番を足すと、OHR 36.30%・BHR 16.08% で、両方とも `moka`（35.89%・11.89%）を上回った。

## 性能のまとめ

### キャッシュのヒット率

| 方式 | OHR | BHR |
|---|---|---|
| LRU（全部入れる） | 14.66% | 8.08% |
| LRU + 2 回目で入れる | 20.23% | 12.86% |
| `quick_cache`（S3-FIFO） | 22.52% | 15.07% |
| LRU + MLP の admission | 25.41% | 17.52% |
| LRU + 未来を見た上限 | 27.13% | 19.14% |
| `moka`（TinyLFU、ML なし） | 35.89% | 11.89% |
| 学習した TTL（α=0.4）+ 頻度の門番 | 36.30% | 16.08% |
| 学習した TTL（OHR だけを最適化）+ 頻度の門番 | 40.32% | 10.12% |

| 実行方法 | 1 行ずつ | まとめて |

### その他

- 精度（キャッシュのテスト AUC）はどの手段でも 0.931〜0.934。次元の多い URL の特徴量だけ、GBDT で 0.984 → 0.995 に上がった。
- learned Bloom filter は、偽陽性率 1% のまま 35.1KB → 7.1KB（int8 で 6.2KB）。ただし問い合わせは 15 倍以上遅く、学習時と違う種類の問い合わせでは偽陽性率が 84% になる。

## 軸ごとの評価（要点）

詳しい表と根拠は `GUIDE.md` の「軸ごとの評価」。

| 手段 | 手軽さ | 性能（質） | 性能（速さ） | ランタイムの重さ | モデルの大きさ | 信頼性 |
|---|---|---|---|---|---|---|
| Rust 自前 | ◎ | ○ | ◎ | ◎ | ◎ | ○ |
| TS 自前 | ◎ | ○ | ○ | ◎ | ◎ | ○ |
| 学習した TTL + 頻度の門番 | △ | ◎ | ○ | ◎ | ◎ | △ |
| `moka` | ◎ | ○ | 未計測 | ○ | — | ◎ |
| learned Bloom filter | ○ | ◎ | △ | ◎ | ◎ | × |
| LightGBM → ONNX Runtime | ○ | ○ | △ | × | △ | ○ |
| JAX（学習の道具） | ○ | ◎ | ◎ | × | ◎ | ○ |
| Rust `std::autodiff`（学習の道具） | × | ◎ | ○ | ○ | ◎ | △ |

- 製品の推論：手軽さ・速さ・軽さ・大きさがすべて ◎ なのは、自前の Rust と TS だけ。まず自前で書く。
- ヒット率を最も高くしたい：学習した TTL + 頻度の門番。ただし合成トレース 1 本・容量 1 つでしか確かめていない。
- 信頼性を最優先：学習なしの `moka`（OHR 重視）か `quick_cache`。

## 落とし穴として分かったこと

- learned Bloom filter の偽陽性率は「問い合わせが学習時と同じ分布なら」という条件付き。
- ML の admission は、作る言語やライブラリより、閾値とキャリブレーション（確率の出方）のほうが結果を動かす。
- Rust `std::autodiff` は、損失を添字（`p[j * D + k]`）で書くと逆伝播が 6 倍遅い。`zip`・`chunks_exact` で書く。
- onnxruntime-node の `run()` は非同期で、同期の判断の中では呼べない。
- `perpetual` は nightly が必要。`ort` は既定でビルド時に `cdn.pyke.io` から取得しようとする（この環境では塞がれていて、npm の `libonnxruntime.so` を実行時に読ませた）。

## まだやっていないこと

- 容量（2% など）やトレースを変えても、「学習した TTL + 頻度の門番」が `moka` より上を保つかの確認。
- 実データでの検証（ここまではすべて合成トレース）。
- 頻度の数え方を、正確な数から近似（count-min sketch など）に変えたときの影響。
- 計測のばらつき（推論の ns は実行ごとに 2 倍近く揺れることがある）。
